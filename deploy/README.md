# Liszt deployment runbook

Everything needed to provision a fresh box and run Liszt on it. No session
history assumed.

Production is **Node 24 running directly under systemd**, fronted by a **Cloudflare
Tunnel**. There is no reverse proxy on the box, no inbound port, and no Docker.
`Dockerfile` and `render.yaml` exist for local/CI use and as an alternative, but
they are not the production path.

The threat model is small and worth stating plainly: the app has **exactly one
perimeter, a single password**. Everything below is arranged so that password is
the only way in.

---

## 1. Preflight (run first, read-only)

Nothing has been verified against a real box. Run these before changing anything.

```sh
cat /etc/os-release          # must be a systemd Debian/Ubuntu-family host
uname -r; nproc; free -h; df -h /
ss -tlnp                    # confirm nothing already owns 3000, 80, 443
systemctl list-units --type=service --state=running
which cloudflared docker caddy nginx
ip route get 1.1.1.1        # stable egress IP?
ufw status 2>/dev/null || firewall-cmd --list-all 2>/dev/null || nft list ruleset
ls -la /etc/cloudflared     # is a tunnel already installed here?
```

**How to read the results.**

| Finding | Consequence |
| --- | --- |
| Not systemd | Stop. The unit in `liszt.service` will not apply; use Docker instead. |
| nginx/Caddy already running | Leave 80/443 alone. The tunnel needs no inbound port, so there is no collision - but do not install a second proxy. |
| Something on 3000 | Change `PORT` in the env file, or stop that service. |
| No stable egress IP | `madouqu.com` direct access and sxyprn both degrade. Leave `LISZT_MADOUQU_API_BASE` on the WordPress.com mirror. |

**Before you start: confirm root SSH works and the key is in your password
manager.** If the app or the tunnel breaks, root SSH is the only way back in.
Consider a non-root sudo user.

## 2. Cloudflare and DNS

1. Add the domain to Cloudflare and point the nameservers at the registrar. This
   propagates slowly and looks like an outage while it happens - **do it early**,
   it should not be on the critical path.
   Confirm with `dig NS <domain>` returning Cloudflare's nameservers.
2. Zero Trust → Networks → Tunnels → create a named tunnel.
3. Run the install command it gives you on the box. This registers a
   `cloudflared` systemd service and writes the tunnel token to
   `/etc/cloudflared/` at mode 600.
   **The token is a credential. It must never reach this repo, a shell history
   file, or a paste.**
4. Public hostname: `liszt.<domain>` → `http://127.0.0.1:3000`.
5. **Do not create a Cloudflare Access application** for this hostname. The app
   gates itself, and a second gate only adds a way to lock yourself out.
6. Security → WAF → Rate limiting: one rule scoped to the `/login` path. This is
   the only route a botnet can push through the tunnel and the only route that
   runs `scrypt`, so limiting it at the edge stops requests costing CPU. The
   app's own in-process throttle is the per-IP backstop, not a replacement.
   Free-plan rule quotas are limited; spend them here.

## 3. Host preparation

```sh
# Service user: no login, no home of value.
useradd --system --shell /usr/sbin/nologin --home-dir /var/lib/liszt liszt

# Code and data, deliberately in different places.
mkdir -p /opt/liszt /var/lib/liszt
chown liszt:liszt /var/lib/liszt
# The database must NEVER live inside the repo: a git clean or a redeploy must
# not be able to reach it.

# Node 24. Do not use nvm - a service must not depend on a shell profile to
# find its runtime.
curl -fsSL https://nodejs.org/dist/latest-v24.x/ | grep -o 'node-v24[^"]*linux-x64.tar.xz' | head -1
# then: tar -xf node-v24*.tar.xz -C /usr/local --strip-components=1

mkdir -p /etc/liszt && chmod 750 /etc/liszt
```

Firewall: leave incoming traffic denied except SSH. The tunnel is outbound, so
80/443 never need to be open. Confirm the current state rather than assuming it.

## 4. Deploy

```sh
cd /opt/liszt
npm ci --omit=dev

# Generate the password hash ON the box, behind a masked prompt, so the
# plaintext never reaches shell history.
npm run auth:hash
```

Put the result in `/etc/liszt/liszt.env`, mode `640`, owned by `root:liszt`:

```sh
cat >/etc/liszt/liszt.env <<'EOF'
NODE_ENV=production
PORT=3000
LISZT_DB_PATH=/var/lib/liszt/liszt.db
LISZT_POLL_INTERVAL_MINUTES=30
LISZT_EPORNER_LQ=0
LISZT_TRUSTED_UPLOADERS=Vovick17,KJUIUI,Rafael12021988,wmrt0s
# Generated by `npm run auth:hash` on this box. NEVER commit this line.
LISZT_AUTH_PASSWORD_HASH=scrypt$...
EOF

chown root:liszt /etc/liszt/liszt.env
chmod 640 /etc/liszt/liszt.env
```

> **The one setting that would expose the app unauthenticated is
> `LISZT_AUTH_DISABLED`.** It must be absent, or explicitly `false`. The service
> also refuses to start if it is set while `NODE_ENV=production` - but verify it
> before the first start rather than trusting the guard.

```sh
cp deploy/liszt.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now liszt

ss -tlnp | grep 3000        # MUST be 127.0.0.1:3000, never 0.0.0.0
```

### Verify in this exact order

```sh
# 1. Unauthenticated liveness returns 401, NOT a health payload. If this returns
#    JSON, auth is not wired and the app is exposed.
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/health

# 2. From another machine, the public hostname shows the password splash.
curl -s -o /dev/null -w '%{http_code}\n' https://liszt.<domain>/

# 3. Log in, then exercise the API with the session cookie.
curl -s -c /tmp/c -X POST -H 'content-type: application/json' \
  -d '{"password":"..."}' https://liszt.<domain>/login -o /dev/null -w '%{http_code}\n'
curl -s -b /tmp/c https://liszt.<domain>/api/scenes | head -c 200

# 4. A wrong password is rejected and looks like a malformed request.
curl -s -X POST -H 'content-type: application/json' \
  -d '{"password":"wrong"}' https://liszt.<domain>/login -w '\n%{http_code}\n'

# 5. No-store, so the edge never caches the catalogue.
curl -s -D- -o /dev/null -b /tmp/c https://liszt.<domain>/api/scenes | grep -i cache-control
```

**Then reboot the box and re-verify every one of those.** Both units must be
enabled:

```sh
systemctl is-enabled liszt cloudflared
reboot
```

This is the most commonly skipped step and it is the one that turns a working
deploy into a 3am outage.

## 5. Configuration reference

Everything except `LISZT_AUTH_PASSWORD_HASH` is optional. Full list in
`.env.example`.

| Variable | Default | Notes |
| --- | --- | --- |
| `LISZT_AUTH_PASSWORD_HASH` | unset | **Required in production.** `scrypt$N$r$p$...` |
| `LISZT_AUTH_DISABLED` | `false` | Local dev only. Refuses to boot in production. |
| `LISZT_LISTEN_ADDR` | `127.0.0.1` | Override only for a platform that fronts the process. |
| `LISZT_DB_PATH` | `data/liszt.db` | Production: `/var/lib/liszt/liszt.db` |
| `PORT` | `3000` | |
| `LISZT_WINDOW_DAYS` | `90` | Rolling window. |
| `LISZT_POLL_INTERVAL_MINUTES` | `30` | Source poll cadence. |
| `LISZT_BOOT_SYNC` | `true` | One sync after listen. |
| `LISZT_FETCH_CONCURRENCY` / `_TIMEOUT_MS` | `4` / `15000` | Outbound bound. |
| `LISZT_TRAXXX_MIN_INTERVAL_MS` / `_CACHE_TTL_MS` | `250` / `300000` | Politeness. |
| `LISZT_MADOUQU_API_BASE` | WordPress.com mirror | Direct `/wp-json` is Cloudflare-challenged. |
| `LISZT_MAXIMO_LISTING_URL` | unset | Unset ⇒ that lane reports "not configured", calmly. |
| `LISZT_TRUSTED_UPLOADERS` | the 4 accounts | **Curation. Back this up.** |
| `LISZT_EPORNER_LQ` | `0` | The API defaults to 1, which *includes* low-quality. |
| `LISZT_MATCH_DURATION_TOLERANCE_SEC` | `2` | Duration band, identical on every rung. |
| `LISZT_MATCH_DATE_WINDOW_DAYS` | `7` | Upload window's upper bound. Lower bound fixed at release − 1 day. |
| `LISZT_POOL_FULL_REWALK_DAYS` | `7` | Drift/deletion correction cadence. |
| `LISZT_SXYPRN_TIMEOUT_MS` | `15000` | |
| `LISZT_SESSION_TTL_DAYS` | `30` | Sliding. |
| `LISZT_LOGIN_MAX_FAILURES` / `_LOCKOUT_MINUTES` | `10` / `15` | Per-IP. Consulted *before* any `scrypt` work. |
| `LISZT_LOG_STDERR` | `false` | JSON logs to stderr; the CLI sets it. |

## 6. Backups

Scenes are rebuildable from upstream on the next poll. What is **not** rebuildable
is the dead-link history, the run ledger, and the trusted-uploader list. Those
are what a backup protects.

```sh
mkdir -p /var/backups/liszt
cat >/etc/systemd/system/liszt-backup.service <<'EOF'
[Unit]
Description=Liszt catalogue backup
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'sqlite3 /var/lib/liszt/liszt.db ".backup /var/backups/liszt-$(date +%%F).db" && find /var/backups/liszt -name "liszt-*.db" -mtime +30 -delete'
EOF
cat >/etc/systemd/system/liszt-backup.timer <<'EOF'
[Unit]
Description=Daily Liszt backup
[Timer]
OnCalendar=daily
Persistent=true
[Install]
WantedBy=timers.target
EOF
systemctl daemon-reload && systemctl enable --now liszt-backup.timer
```

Use **`.backup`, never `cp`.** The database runs in WAL mode, and a plain copy of
a hot database is not consistent.

**Test a restore.** An untested backup is not a backup, and this is the step that
always gets skipped:

```sh
sqlite3 /var/backups/liszt/liszt-$(date +%F).db ".backup /tmp/restore-test.db"
sqlite3 /tmp/restore-test.db "PRAGMA integrity_check;"   # expect: ok
```

Consider copying backups off the box. A backup that dies with the VPS protects
against nothing that matters.

## 7. Operations

```sh
systemctl status liszt
journalctl -u liszt -f            # JSON lines; the ts/level/component fields are the filter
journalctl -u liszt -n 200 --no-pager
systemctl restart liszt
```

**Reading the logs.** Every line is JSON.

| Message | Meaning |
| --- | --- |
| `sync started` / `sync finished` | One cycle. `matched`/`resolved`/`reverified` are its numbers. |
| `sync: source ok` | That source returned records. |
| `sync: source failed, retaining last-good records` | One source failed. **The others still ran, and nothing was deleted.** The dashboard's Sources page shows the same state. |
| `pool index incomplete` | A trusted account's profile walk failed. The ladder still runs; rung 1 is just thinner. |
| `optional sxyprn client not installed` | Expected if the optional dependency is absent. Rung 2 is disabled; eporner carries those scenes. |

Force a cycle without waiting for the timer: `POST /api/refresh` from the
dashboard, or:

```sh
curl -s -b /tmp/c -X POST https://liszt.<domain>/api/refresh
```

It returns `202` immediately and joins the in-flight cycle if one is running.
The dashboard polls until it settles.

### Rolling back

The database is schema-versioned and additive; an older build ignores unknown
tables. To roll back:

```sh
systemctl stop liszt
cd /opt/liszt && git checkout <previous-tag> && npm ci --omit=dev
systemctl start liszt && journalctl -u liszt -f
```

Take a backup first. A schema migration is never applied twice, but a downgrade
does not un-apply anything.

### Rotating the password

```sh
systemctl stop liszt
cd /opt/liszt && npm run auth:hash      # masked prompt, on the box
# replace the LISZT_AUTH_PASSWORD_HASH line in /etc/liszt/liszt.env
systemctl start liszt
```

Existing sessions survive a password change (they are DB-backed rows, not signed
tokens) - they are not revoked by rotating the password. To log everyone out,
delete the rows: `sqlite3 /var/lib/liszt/liszt.db "DELETE FROM sessions;"`.

### Upgrading Node

The runtime is pinned at `/usr/local/bin/node`. Move it deliberately:

```sh
systemctl stop liszt
# install the new tarball over /usr/local
node --version
cd /opt/liszt && npm ci --omit=dev && npm test
systemctl start liszt && journalctl -u liszt -n 50 --no-pager
```

`npm test` before restarting: an upgrade that breaks the suite should not reach
production.

## 8. Calibration note

The pool rung runs first, deliberately, because the four trusted accounts carry
most of the traxxx-lane releases. It is not a looser gate any more: every rung
applies the same two eligibility rules and the same ranking. It is a *cheaper*
rung, because the index answers it without a search request per scene.

**Measured on the live pool (2026-09):** the trusted uploaders title their
uploads in an obfuscated convention, using only first names for
multi-performer scenes. That is why performer-in-title is a *ranking tier*
rather than a pass/fail gate — a strict identity rule would score the whole
trusted pool at zero and hand every match to a decoy.

Before trusting the window or changing it, run the measurement rather than
guessing:

```sh
cd /opt/liszt && npm run calibrate
```

It reports a lag histogram over every duration-surviving candidate (not just
the winners, which would be self-confirming), a per-stage funnel, unknown-date
counts, and the identity-tier histogram of the winners. Set
`LISZT_MATCH_DATE_WINDOW_DAYS` from that histogram, not from taste. The window
is a knob rather than a constant precisely so that widening it is an env change
and a re-run.

## 9. Security checklist

- [ ] `LISZT_AUTH_DISABLED` absent or `false`
- [ ] `LISZT_AUTH_PASSWORD_HASH` set, generated on the box
- [ ] `ss -tlnp` shows `127.0.0.1:3000`, never `0.0.0.0`
- [ ] `/api/health` returns **401** unauthenticated
- [ ] `/etc/liszt/liszt.env` is `640 root:liszt`; tunnel token `600`
- [ ] Neither file, nor their contents, is in git
- [ ] Cloudflare rate limit engaged on `/login`
- [ ] Incoming firewall denies everything but SSH
- [ ] `systemctl is-enabled liszt cloudflared`, **verified after a reboot**
- [ ] `Cache-Control: no-store` on API responses
- [ ] A backup restores and passes `PRAGMA integrity_check`
- [ ] `journalctl -u liszt -n 200` shows no unhandled errors

## 10. Known limits

- **One password is the whole perimeter.** Keep it long and unique; the edge
  rate-limit rule and the in-process throttle are the DoS/guessing counterweights.
- **The throttle is in-memory.** One process only. A second instance requires
  moving it to the database.
- **sxyprn answers 403 from datacenter IPs.** Rung 2 will frequently be dead in
  production and eporner open search carries those scenes despite being rung 3.
  Source health is meant to make this visible rather than surprising you later.
- **No inbound port means no direct fallback.** If Cloudflare is down, SSH plus a
  local port-forward is the manual way in. Decide in advance that this is
  acceptable.
- **The FC2 lane is a stub.** `fc2cmadb.com`'s interface is unconfirmed; the lane
  reports a setup gap and never trips the empty-source protection.
- **Pool coverage is measured only for the traxxx lanes.** Bang!, Maximo and
  madouqu may have little or no pool presence.
